## 三、P0 级（上线前必须修）

### P0-1 设定本拼版：无限重试 + 无并发锁 → ffmpeg 进程风暴【最严重】

**位置**
- `backend/src/modules/comic-studio/comic-studio.service.ts` → `status()`（约 805–820 行）
  ```ts
  if (!c.sheet_url && c.blocks.every((b) => b.url)) {
    try {
      const url = await this.assembleSheet(p, c);       // ← 每次轮询都可能跑一次 ffmpeg
      if (url) { c.sheet_url = url; dirtyChars = true; }
    } catch (e: any) { this.logger.warn(`设定本拼版失败 ${c.id}: ${e.message}`); }
  }
  ```
- `assembleSheet()` 572–590 行：`execFileAsync(ffmpegBin, [...], { timeout: 90000 })`，4 路 768×768 PNG 解码 + `xstack`
- 前端 `ComicStudio/index.tsx` 124–140 行：`setInterval(tick, 3000)`，**不等待上一次请求完成**

**问题链**
1. 拼版失败后只 `warn`，**不写失败标记、不加冷却、不重试计数** → 条件永远成立
2. 前端每 3 秒轮询一次 `status()` → 每 3 秒起一个 ffmpeg
3. 单次 ffmpeg 超时 90 秒 → 90 秒窗口内最多 **30 个并发 ffmpeg**（多个标签页/多个用户再乘倍数）
4. 前端 `setInterval` 不检查 in-flight，status 接口挂 90s 时请求持续堆积，进一步放大
5. 无 in-flight 锁：同一人物多个并发 `status()` 会同时写同一个 `sheet_<id>.png`，文件互相覆盖损坏

**触发条件非常常见**（尤其刚加了「素材图」来源）：任一块图路径失效、被清理、格式异常、导入时被并发写坏、或文件被用户删掉。用户测试时踩到一次，实例就会在几分钟内被打死。

**修法**
- 在 service 上加 `private sheetInflight = new Set<string>()`（或 Map 存 Promise），按 `projectId:characterId` 去重，进行中直接跳过
- 拼版失败写 `c.sheet_error` + `c.sheet_retry_at`（指数退避，如 30s → 5min），成功清空；连续失败 N 次后停止自动重试，由前端「重新拼版」按钮手动触发
- 把拼版从只读的 `status()` 里挪出去，改为块任务全部完成时的回调 / 独立端点
- 前端轮询改为 `setTimeout` 递归 + in-flight 标志（或 AbortController），保证任何时刻只有 1 个在途请求
- `assembleSheet` 输出到临时文件再原子 `rename`，避免并发写半截文件

### P0-2 `void` Promise 无 catch + 全局无兜底 → 未处理拒绝直接杀进程

**位置**
- `generate.service.ts:683 / 838`：`void this.updateProgress(task, ...)`；而 `updateProgress()`（157–161 行）只有 `await this.taskRepo.update(...)`，**没有 try/catch**
- `comic-studio.service.ts:908`：`void archive.finalize()`（archiver finalize 返回 Promise，无 catch）
- `backend/src/main.ts`：**全文没有** `process.on('unhandledRejection' | 'uncaughtException')`；全库 grep 零命中

Node 22 默认 `--unhandled-rejections=throw`。因此 **DB 连接池抖一下、磁盘写满、archiver 出错 → 整个 Node 进程退出**，所有在跑的任务变成孤儿（虽有 TaskRecovery 兜底退款，但生产会 502 + pm2 重启）。生产又没设 `max_memory_restart`、没有崩溃前日志。

**修法**：给 3 处 `void` 补 `.catch(...)`（或把 `updateProgress` 内部包 try/catch 并返回安全值）；在 `main.ts` 加 `process.on('unhandledRejection'/'uncaughtException')` 记录日志（只记不吞，让 pm2 重启）；pm2 设 `max_memory_restart: '600M'` 做最后一道熔断。

> 已核实**安全**的同类调用：`void this.enqueue(...).catch(...)`（9 处都有 catch）、`void this.generateAutoCover(...)`（方法内部 1241–1270 有完整 try/catch）、`startHeartbeat` 的 `.catch(() => undefined)`。

### P0-3 `execFileSync('ffmpeg')` 同步阻塞事件循环

**位置**：`backend/src/utils/ai-service.util.ts:1664 / 1674 / 1703 / 1715`（占位视频 / 紧急降级路径），`timeout: 15000`，最内层兜底还有一次 `10000`。

同步执行期间 **整个事件循环停摆**：所有 HTTP 请求、20s 心跳、健康检查全部无响应 → nginx 502；心跳停摆超过阈值还可能被 `TaskRecoveryService` 误判孤儿并退款。生产 `/usr/bin/ffmpeg` 存在，降级路径一旦触发就是连续 15~25 秒全站不可用。

**修法**：改 `execFileAsync`（项目里已有 `ffmpeg.util.ts` 的 `runFfmpegQueued` 可直接复用），不要在请求线程里跑同步子进程。

### P0-4 生产缺表 / 缺迁移 / lock 未同步（确定性故障）

- 远程实测 `comic_projects` 表 **不存在**；生产 `DB_SYNCHRONIZE=0`，迁移 `1794130000000-AddComicProjects.ts` **从未执行** → V2 全部端点、开源图鉴页 100% 500
- 生产 `prompt_templates` 也没有 4 条 comic 模板（会走 service 内置兜底，不致命，但后台不可配置）
- 11-06 补过生产 `backend/package.json` 两条依赖声明，**`package-lock.json` 仍未同步**：一旦在生产跑 `npm ci`，会再次出现 `@nestjs/schedule` / `winston-daily-rotate-file` 缺失 → 502 重演
- 生产 `model_configs` 仍只有 2.5 active（代码用白名单不依赖 DB，但管理后台列不出 2.1）

**修法**：上线前按 `docs/deploy.md` 流程跑迁移（或临时 `DB_MIGRATIONS_RUN=1`）、同步 4 条模板、补 2.1 模型配置；把 `package-lock.json` 一并对齐后再允许任何 `npm ci`。

## 四、P1 级（会导致卡死 / 数据错 / 资金损失）

### P1-5 `startGeneration` 死锁 + 并发重复扣费

`comic-studio.service.ts:722–757`：
- 循环里任一组 `createComicPanelTask` 抛错就 `break`，但循环后**无条件** `p.status = 'generating'`，且 `saveSpec(p, spec)` 用 `repo.save(p)` 把状态持久化
- 若**第一组就失败**（`created.length === 0`，例如积分不足 / 参考图校验失败），项目永久停在 `generating`：`status()` 里 `all = panels.filter(x => x.task_id)` 为空，`if (p.status === 'generating' && all.length && ...)` 永远不成立 → 不会回写 completed；而 `startGeneration` 开头 `if (p.status === 'generating') throw '已在生成中'` → **用户再也点不了生成，只能手工改库**
- `if (p.status === 'generating')` 是读-改-写，**无事务/无唯一约束**，两个并发请求可同时通过 → 双倍建任务、**双倍预扣积分**

**修法**：`created.length === 0` 时把状态回退到 `script_review` 并抛错；改为带条件的原子 `UPDATE ... WHERE status <> 'generating'`（affected=0 即拒绝重复提交）；部分组失败时要么回滚已扣积分，要么明确告知用户「成功 N 组 / 失败 M 组」并允许续跑。

### P1-6 图鉴导入：临时文件泄漏 + 并发写坏 + 残片当有效图

`comic-studio.service.ts:340–386`：
- `await downloadToFile(raw, tmp, ...)` 写在 **`try { } finally { 删 tmp }` 之外** → 下载失败时留下最多 25MB 的 `.<id>_<ts>.raw`，反复失败持续累积，且会被算进 500MB 配额
- 同 id 并发导入：两个请求都看到 `dest` 不存在 → 同时下载、同时 ffmpeg 写同一个 `<id>.jpg` → 文件损坏
- 配额检查是 TOCTOU（并发都未超限，都放行）
- ffmpeg 写一半失败留下**非 0 字节残片**，下次去重判断 `size > 0` 会把它当有效图秒回 → 永久坏图，进而**触发 P0-1 的拼版风暴**

**修法**：把 `downloadToFile` 挪进 try；输出到 `.tmp` 再原子 rename；按 id 加进程内锁；启动时清理 `.*.raw` 残留；压缩后校验 JPEG 头/可解码再落正式文件。

### P1-7 图鉴目录惊群 + 外网失败无兜底

`comic-studio.service.ts:292–335`：缓存到期后 N 个并发请求会**同时**发两份外网 axios（无 in-flight Promise 复用）；外网 30s 超时时全部挂住；请求失败**不回退到过期缓存** → 图鉴整页 30s 不可用。`fs.writeFileSync` 同步写几 MB 缓存也会短暂停住事件循环。

**修法**：用 `private openCatalogInflight: Promise<any> | null` 复用在途请求；catch 时优先返回过期缓存并打 warn；缓存写改异步 `fs.promises.writeFile`。
